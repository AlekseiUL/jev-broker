# JEV Broker

Применяй этот скилл, когда короткая оценка найденных кандидатов может изменить следующий шаг: отбор, классификацию или порядок глубокого чтения. Он не делает поиск и не заменяет анализ первоисточников. Скилл учит пользоваться инструментом, но сам не подключает MCP и не выдаёт права.

## Сначала проверь доступ

Найди в текущем списке инструментов `evaluate` сервера `jev_broker` (обычное имя Hermes — `mcp__jev_broker__evaluate`). Если его нет, сообщи, что Broker не подключён; не изображай вызов JEV и не проси пользователя прислать ключ.

## Выбери задачу самостоятельно

1. Сформулируй решение, которое изменится от оценки. Если решение не изменится, не вызывай JEV.
2. Получи кандидатов законным инструментом поиска/чтения. JEV не читает Telegram, файлы или базы сам.
3. Составь собственные `state` или `items` и именованные `questions`; не ограничивайся примерами ниже. `state` — один материал или общий контекст. `items` — несколько записей по ID; каждый item станет отдельным платным запросом, выполняемым последовательно.
4. Для каждого вопроса выбери подходящий режим:
   - `noul`: точный вопрос «да/нет», возвращает вероятность «да» 0–1. Можно задать `criteria` с описаниями `true`/`false`.
   - `choice`: выбор среди твоих `options`, возвращает вариант и распределение вероятностей. Добавь `none_unknown`, если ни один вариант может не подойти.
   - `score`: оценка по твоему упорядоченному `rubric` из 2–10 ясно описанных уровней. Балл — положение между этими уровнями, не процент «качества».
5. При необходимости задай `min_confidence` для `noul`/`choice`, чтобы увидеть неопределённость. Не маскируй сомнительные решения как точные.
6. Сопоставь ответ по ID с исходными данными, проверь существенные выводы и только затем решай, что читать глубже или показывать пользователю. Ошибку/пустой результат не считай отрицательной оценкой; не повторяй автоматически платный вызов, исход которого неизвестен.

## Форма вызова

`evaluate` принимает один JSON-объект с `questions` и либо непустым `state`, либо непустыми `items`. Каждый вопрос имеет `mode`, `task` и поля режима: `criteria` для `noul`, `options` для `choice`, `rubric` для `score`. Можно смешивать режимы в одном запросе.

Технические пределы вызова: вход до 1 МиБ, исходящий JSON до 4 МиБ, не более 8 `items` (каждый — платный запрос) и 64 вопросов; `choice` — до 255 вариантов, `score` — 2–10 уровней. Для профиля действует счётчик 32 запросов за день UTC в памяти Broker: перезапуск его сбрасывает, это не денежный бюджет. Общий `state` повторно отправляется с каждым item — передавай только разрешённые данные. Это не ограничение тем или критериев — их выбираешь ты.

Синтетический пример; для реальной задачи придумай свои критерии:

```json
{
  "state": {"goal": "Найти прямые жалобы на задержку ответа"},
  "items": {
    "example-1": {"text": "Написал вчера, ответа пока нет"},
    "example-2": {"text": "Во вторник выйдет обновление"}
  },
  "questions": {
    "relevant": {"mode": "noul", "task": "Есть ли конкретная жалоба на задержку ответа?"},
    "kind": {"mode": "choice", "task": "Какой это тип сообщения?", "options": {"complaint": "жалоба", "news": "новость", "none_unknown": "неясно"}},
    "strength": {"mode": "score", "task": "Насколько силён сигнал для этой темы?", "rubric": ["не по теме", "косвенно", "прямой случай"]}
  }
}
```

## Границы

Не передавай API-ключи, bearer-токены, пароли, cookie или файлы сессий. Перед отправкой чужих сообщений и клиентских данных проверь право на обработку во внешнем сервисе. JEV — вероятностная оценка, не источник фактов и не разрешение писать людям или менять данные. Экономия контекста возникает, только если кандидаты фильтруются до загрузки их полных текстов в большой агентский контекст.
