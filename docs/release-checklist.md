# Перед публикацией на GitHub

Этот каталог — подготовка публичного пакета, **не опубликованный репозиторий**. Нельзя копировать целиком рабочую папку действующего сервиса: там бывают журналы, приватные конфиги, токены, файлы состояния, бинарники и старые схемы. Публикуйте только проверенный экспорт.

## Разрешённый состав

- `README.md`, `AGENT_GUIDE.md`, `LICENSE`, `NOTICE`, `.gitignore`, `go.mod`, `go.sum`;
- исходники и тесты `cmd/jev-broker/*.go`, `internal/broker/*.go`;
- инструкции `docs/*.md` и безопасные помощники `scripts/*.py`.
- общий Hermes-скилл `skills/jev-broker/SKILL.md`.

В публикации **не должно быть** `bin/`, `.env`, `openrouter.key`, `clients.json`, `audit.log`, `profile-*.env.fragment`, логов, `.state`, `.session`, приватных YAML, резервных копий, `.git` другого репозитория или реальных примеров сообщений. Даже хеши действующих bearer-токенов и реальные ID/пути команды автора не нужны подписчику.

## Проверка перед push

1. Создайте новый чистый каталог/репозиторий только из перечисленных файлов. Не переносите `.git` и историю рабочего сервиса.
2. Запустите из корня пакета `python3 scripts/release_check.py`. Он проверяет allowlist и некоторые формы секретов, выводя **только имя файла и правило**, не найденное значение. После создания отдельного Git-репозитория и до push повторите `python3 scripts/release_check.py --require-standalone-git`: проверяются также index и все коммиты этого **нового** репозитория. Если проверка упала, публикация остановлена.
3. Дополнительно запустите специализированный сканер секретов по файлам и всей новой Git-истории; этот скрипт его не заменяет. В данной рабочей среде такой сканер заранее не установлен. Вручную просмотрите `git status`, `git diff --cached --name-only`, изменения и финальный список файлов, не выводя значения секретов в отчёт.
4. На чистой копии без настоящего ключа выполните `go test ./...`, `python3 -B -m unittest discover -s scripts -p 'test_*.py'`, `go build -o bin/jev-broker ./cmd/jev-broker`. Протестируйте setup на вымышленном ключе во временной приватной папке и `run.py --check`. Go-тесты с мок-провайдером проверяют отказ без bearer/с чужим bearer и получение `tools/list`; затем проверьте `tools/list` в своей установленной Hermes-среде. Реальный платный вызов — только отдельное решение владельца после установки.
5. Проверьте, что документация совпадает с фактическими именами env, JSON-конфигом, CLI и схемой MCP. Подписчик должен получить один общий инструмент и право самому задавать `state`, `items`, `questions`, а не старый каталог фиксированных постов.
6. Согласуйте конкретные GitHub-репозиторий и видимость, затем публикуйте только проверенную копию. До этого пункта не делайте push и не называйте пакет опубликованным.

`release_check.py` — эвристическая защита, не гарантия отсутствия любого ключа или персональных данных. Если секрет всё-таки попал в Git, одного удаления из последнего коммита недостаточно: отзовите ключ и очистите всю публикуемую историю до выпуска.
