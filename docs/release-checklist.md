# Проверка перед публичным выпуском / Public release checklist

Этот каталог — исходники отдельного публичного пакета. Перед каждым новым push собирайте и проверяйте чистую копию; не переносите рабочую папку действующего сервиса или историю другого репозитория. В них могут быть журналы, приватные конфиги, токены, файлы состояния, бинарники и старые схемы. Опубликованная ветка не становится безопасной только потому, что новый README выглядит чисто.

## Разрешённый состав

- `README.md`, `AGENT_GUIDE.md`, `LICENSE`, `NOTICE`, `.gitignore`, `go.mod`, `go.sum`;
- только `.github/workflows/offline-checks.yml` для офлайн-проверок PR (без секретов и платных вызовов);
- исходники и тесты `cmd/jev-broker/*.go`, `internal/broker/*.go`;
- инструкции `docs/*.md` и безопасные помощники `scripts/*.py`.
- общий Hermes-скилл `skills/jev-broker/SKILL.md`.

В публикации **не должно быть** `bin/`, `.env`, `openrouter.key`, `clients.json`, `audit.log`, `profile-*.env.fragment`, логов, `.state`, `.session`, приватных YAML, резервных копий, `.git` другого репозитория или реальных примеров сообщений. Даже хеши действующих bearer-токенов и реальные ID/пути команды автора не нужны подписчику.

## Проверка перед push

1. Для первого выпуска создайте отдельный репозиторий только из перечисленных файлов; для обновления работайте с чистой копией **этого** репозитория. Никогда не переносите `.git` и историю рабочего сервиса или другого проекта.
2. Запустите из корня пакета `python3 scripts/release_check.py`, затем `python3 scripts/release_check.py --require-standalone-git`: проверяются allowlist, типовые формы секретов, index и все доступные коммиты **этого** отдельного репозитория. Скрипт выводит только имя файла и правило, не найденное значение. Если проверка упала, push остановлен.
3. Дополнительно запустите специализированный сканер секретов по файлам, архиву и всей Git-истории; этот скрипт его не заменяет. Вручную просмотрите `git status`, `git diff --cached --name-only`, изменения и финальный список файлов, не выводя значения секретов в отчёт.
4. На чистой копии без настоящего ключа выполните `go test ./...`, `python3 -B -m unittest discover -s scripts -p 'test_*.py'`, `go build -o bin/jev-broker ./cmd/jev-broker`. Протестируйте setup на вымышленном ключе во временной приватной папке и `run.py --check`. Go-тесты с мок-провайдером проверяют отказ без bearer/с чужим bearer и получение `tools/list`; затем проверьте `tools/list` в своей установленной Hermes-среде. Реальный платный вызов — только отдельное решение владельца после установки.
5. Проверьте, что документация совпадает с фактическими именами env, JSON-конфигом, CLI и схемой MCP. Подписчик должен получить один общий инструмент и право самому задавать `state`, `items`, `questions`, а не старый каталог фиксированных постов.
6. Перед первым выпуском согласуйте адрес и видимость GitHub-репозитория. При следующих обновлениях повторно сверяйте `origin`, ветку, список файлов и приватность/публичность **до** push; не добавляйте чужие файлы или историю.

`release_check.py` — эвристическая защита, не гарантия отсутствия любого ключа или персональных данных. Если секрет всё-таки попал в Git, одного удаления из последнего коммита недостаточно: отзовите ключ и очистите всю публикуемую историю до выпуска.
